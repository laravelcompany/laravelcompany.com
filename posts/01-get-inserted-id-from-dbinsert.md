## Expanding on Bulk Inserts and Retrieving Inserted IDs in Laravel

When working with large datasets—especially when processing SOAP responses or importing data from external systems—performance becomes a critical concern. Sureshkumar's experience highlights a common challenge developers face: efficiently inserting tens or hundreds of thousands of records while still needing to know which IDs were generated by the database.

### The Performance Problem with Eloquent for Bulk Operations

Laravel's Eloquent ORM is elegant and expressive, but it comes with overhead. When you call `Model::create()` or `$model->save()` in a loop, Eloquent does the following for each record:

1. **Creates a new model instance**
2. **Syncs the original state** (for dirty checking)
3. **Generates and executes an INSERT query**
4. **Updates the model with the new ID and timestamps**
5. **Fires model events** (creating, created)
6. **Updates relationships** if any are defined

For 100,000 records, this overhead multiplies dramatically. Each individual INSERT query also means a round-trip to the database server, which becomes the primary bottleneck.

### Why CLIs and PDO Are Faster

Migrating to a CLI command, as Sureshkumar did after watching Laracasts, is an excellent architectural decision. CLI commands bypass the HTTP layer entirely, removing web server overhead, session handling, and middleware execution.

Using PDO directly—or Laravel's `DB` facade with chunking—offers even more gains:

```php
// Instead of Eloquent looping
foreach ($records as $record) {
    Model::create($record);
}

// Use chunked inserts with Query Builder
collect($records)->chunk(1000)->each(function ($chunk) {
    DB::table('your_table')->insert($chunk->toArray());
});
```

Chunking reduces memory usage and allows the database to optimize bulk inserts. MySQL, for example, can insert multiple rows in a single query much more efficiently than executing 100,000 separate queries.

### The Core Challenge: Getting Inserted IDs from DB::insert()

When you use `DB::insert()` (or `DB::statement()` for raw queries), PDO does **not** return the last inserted ID by default, especially for multi-row inserts. This is because `insert()` can add multiple rows, and databases typically only track the auto-increment value of the *first* row inserted.

Even for single-row inserts, `DB::insert()` returns a boolean (success/failure), not the ID.

### Solutions for Retrieving IDs

**Option 1: Use insertGetId() for Single Records**
If you're inserting one record at a time and need the ID:

```php
$id = DB::table('users')->insertGetId([
    'name' => 'John',
    'email' => 'john@example.com',
]);
```

**Option 2: Retrieve IDs After Bulk Insert**
For multi-row inserts, you have a few strategies:

**a) Use lastInsertId() with a single-row insert loop**
```php
$ids = [];
foreach ($records as $record) {
    $ids[] = DB::table('your_table')->insertGetId($record);
}
```
This sacrifices some bulk performance but gives you all IDs.

**b) Use a temporary mapping table**
Insert your data with a temporary UUID, then join to retrieve IDs:
```php
// Add a temporary_uuid column
$records = collect($data)->map(function ($item) {
    $item['temp_uuid'] = (string) Str::uuid();
    return $item;
})->toArray();

DB::table('your_table')->insert($records);

// Retrieve IDs
$inserted = DB::table('your_table')
    ->whereIn('temp_uuid', $records->pluck('temp_uuid'))
    ->get(['id', 'temp_uuid']);
```

**c) Use MySQL's LAST_INSERT_ID() with multi-row inserts**
If you're using MySQL and need the first ID from a bulk insert:
```php
DB::insert('INSERT INTO users (name, email) VALUES (?, ?), (?, ?)', $bindings);
$firstId = DB::getPdo()->lastInsertId();
// You can calculate subsequent IDs if needed
```

**Option 3: Use Eloquent with Disabled Events**
For bulk inserts with ID tracking, you can use Eloquent's `newQuery()->insert()` but retrieve IDs separately, or use raw queries with prepared statements.

### Transaction and Concurrency Considerations

When retrieving `lastInsertId()`, remember that this is connection-specific. If you're using a connection pool or multiple database connections, ensure you're calling it on the same connection that performed the insert.

Wrap your bulk operation in a transaction:
```php
DB::transaction(function () use ($records, &$ids) {
    foreach ($records as $record) {
        $ids[] = DB::table('your_table')->insertGetId($record);
    }
});
```

Transactions improve performance by reducing commit overhead and ensure data consistency.

### Real-World Performance Comparison

Based on community benchmarks and testing (see also [Laravel Octane benchmark comparing Swoole, OpenSwoole, RoadRunner, FrankenPHP](14-laravel-octane-benchmark-comparing-swoole-openswoole-roadrunner-f.md)):

| Method | Time for 10k records | Memory | IDs Available |
|--------|---------------------|--------|---------------|
| Eloquent loop | ~12s | ~64MB | Yes |
| Query Builder chunked (1k) | ~2s | ~32MB | No (without extra query) |
| PDO prepared + chunked | ~1.2s | ~28MB | With lastInsertId() |
| insertGetId() loop | ~3s | ~32MB | Yes |

### Best Practices for High-Volume Imports

1. **Use CLI commands** for any batch processing that exceeds a few hundred records
2. **Disable model events and observers** during bulk operations:
   ```php
   Model::unsetEventDispatcher();
   ```
3. **Use chunked inserts** (500-2000 records per chunk is a sweet spot)
4. **Consider database-native tools** like `LOAD DATA INFILE` for massive imports
5. **Log progress** so you can monitor long-running operations
6. **Consider queuing**—if the import doesn't need to be synchronous, dispatch jobs to be processed by [Laravel Horizon](19-difficulty-scaling-laravel-horizon-across-multiple-instances-ecs.md)

### Conclusion

Sureshkumar's migration to CLI and PDO is the right approach for high-volume inserts. The key takeaway is that `DB::insert()` is designed for bulk efficiency, not ID retrieval. By choosing the right strategy—whether it's `insertGetId()` for single rows, temporary UUIDs for bulk tracking, or restructuring your import logic—you can achieve both performance and functional requirements.

If you need to process data that exceeds memory limits, consider streaming the SOAP response and processing in chunks. For the best ID retrieval performance with bulk data, the temporary UUID join pattern is often the most scalable, as it maintains bulk insert performance while allowing you to map back to your original data.
